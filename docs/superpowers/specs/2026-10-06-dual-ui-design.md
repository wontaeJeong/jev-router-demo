# Router demo: 공통 코어, Textual TUI, 로컬 웹 대시보드

## 목표와 승인된 방향

기존 Python + Rich CLI를 발표에 적합한 비교 데모로 개선한다. Python의 HTTP
adapter와 측정 로직을 재사용하고, Textual TUI와 로컬 웹 대시보드를 제공한다.
두 UI에서 실제 HTTP 요청·응답 바디를 확인할 수 있게 한다. 긴 문자열은 기본
화면에서 중략하며 실제 전송·저장 원본은 변경하지 않는다.

사용자는 2026-10-06에 공통 코어 기반 TUI + 로컬 웹 구성을 승인했다.
이 문서는 구현 전 검토할 상세 설계다.

### 추가 요구사항: 실제 Jev System One / Decisions (2026-10-07)

사용자는 구현 중 OpenRouter Decisions endpoint 지원을 함께 추가하도록 승인했고,
Jev는 Ollama 생성 모델이 아닌 System One 스타일이라는 점을 확인했다.
이 추가사항은 아래의 기존 Ollama-only 설명에 우선한다.

- `JEV_API_MODE=systemone | decisions | ollama`로 전송 계약을 명시한다.
- System One과 Decisions는 공통 `model + state + questions → answers + usage`
  adapter로 처리한다. endpoint URL을 지정하면 경로를 덧붙이지 않는다.
- OpenRouter의 두 공식 경로는 `https://openrouter.ai/api/v1/systemone`과
  `https://openrouter.ai/api/alpha/decisions`다. 로컬 호환 endpoint도 지원한다.
- `JEV_ENDPOINT_URL`이 없으면 `JEV_BASE_URL`에 모드별 `/v1/systemone`,
  `/alpha/decisions`, `/api/generate`를 붙인다. 인증은 별도의 `JEV_API_KEY`를 사용한다.
- 새 `.env.example`은 `systemone`을 기본 예시로 제공한다. 기존 환경에서 모드를
  생략한 경우는 `ollama`로 유지하며 런타임 API 자동 추정은 하지 않는다.
- 세 질문 모두 Choice를 사용한다. model tier는 `fast/standard/reasoning`,
  web/approval은 `true/false` label로 명시적 매핑한다. 숨겨진 Noul threshold는 없다.
- 응답 answer type·label·확률 범위를 검증하고 API가 제공한 확률만 표시한다.
  raw API response와 실제 전송 request는 다른 adapter와 같은 방식으로 보관한다.
- typed 결과는 `output_kind=typed`, `parse_required=False`다. typed validation과
  HTTP JSON decoding은 latency에 포함하며 generated-decision parse time은 미제공이다.
  API가 반환한 input/output token usage를 그대로 쓰고 output tokens를 0으로 만들지 않는다.
- 실제 생성 문자열·thinking이 없으므로 generated text/bytes는 미제공으로 표시한다.
- 두 UI의 API mode 안내는 실제 설정에 따라 바뀐다. Ollama는 호환용 generated
  fallback임을 명시하고 실제 Jev System One API와 구분한다.

출처: [System One](https://openrouter.ai/docs/guides/community/typesafe-sdk),
[Decisions](https://openrouter.ai/docs/guides/community/jev-tutorial).

## 기술 선택과 실행

- Python 3.12+, httpx, Pydantic, 기존 LiteLLM/Ollama adapter를 유지한다.
- TUI는 Textual을 사용하고 Rich renderable을 결과·JSON 표현에 활용한다.
- 웹은 FastAPI + Uvicorn으로 제공한다. HTML/CSS/JavaScript를 Python 패키지에
  포함하여 별도 Node 빌드와 CDN 없이 실행한다.
- `uv run jev-router-demo`는 TUI를, `uv run jev-router-demo --web`은
  `http://127.0.0.1:8000`의 웹 대시보드를 실행한다. 웹 포트는 옵션으로 지정한다.
- 설정은 현재의 환경변수와 작업 디렉토리 `.env.local` 로딩을 유지한다.
  웹 브라우저는 로컬 Python 서버를 통해 모델을 호출한다.
- 두 UI는 동일한 코드를 사용하지만 각각 독립 세션이다. TUI 실행과 브라우저,
  또는 서로 다른 브라우저 연결 사이에서 누적 지표를 동기화하지 않는다.

## 공통 데이터 모델과 HTTP 기록

`RoutingResult`에 HTTP 기록을 연결한다. HTTP 기록에는 POST method, URL,
실제 요청 JSON 객체, HTTP status, 응답 텍스트와 디코딩된 응답 JSON을 담는다.
인증 헤더는 기록하거나 UI로 전달하지 않는다.

전송 경계인 `request_route()`에서 요청 바디를 캡처한다. parser가 새 결과 객체를
반환해도 HTTP 기록을 최종 결과에 연결한다. 성공 응답, HTTP 오류, 비 JSON,
잘못된 envelope, decision parse 오류에서 기록이 유지되어야 한다.
연결 실패·timeout에서는 요청 기록은 남기고 응답은 '응답 없음'으로 표시한다.

HTTP response의 JSON 디코딩 성공 여부와 decision parse 성공 여부를 구분한다.
JSON인 HTTP 오류 응답도 JSON으로 탐색할 수 있다. JSON이 아닌 오류 바디는
텍스트로 표시한다. 원본 텍스트와 decoded JSON을 함께 보관하여 전체 원문 보기와
JSON 가독성 보기를 지원한다. 실제 byte-level packet capture는 범위에 포함하지 않는다.
JSON nesting이 formatter가 지원하는 깊이를 초과하면 원문 텍스트로 표시하고,
해당 backend 오류가 다른 backend의 정상 결과 전달을 막지 않게 한다.

## 공통 실행 서비스

UI에 의존하지 않는 비교 서비스를 추가한다. 두 adapter를 동시에 실행하고
각각 완료되는 즉시 결과 이벤트를 전달한다. 서비스가 run ID, 결과 snapshot,
실행 상태와 세션 누적 지표를 관리한다.

- 상태: `idle → running → success | error`, 각 router에 독립 적용.
- 시작 시 요청 문자열과 scenario 정보를 snapshot으로 고정한다.
- 결과마다 누적 지표를 정확히 한 번 반영한다.
- 실행 중에는 재실행·시나리오 전환·요청 편집을 비활성화한다. JSON 탐색과
  화면 스크롤은 계속 사용할 수 있다. 이전 결과를 새 실행 결과처럼 표시하지 않는다.
- 한 backend가 실패해도 다른 backend는 정상 완료하며 부분 결과를 유지한다.
- 앱 종료·웹 연결 종료 시 진행 중 작업을 취소하고 HTTP client를 정리한다.
  완료되지 않은 취소 작업은 성공·오류 측정에 추가하지 않는다.
- 세션은 현재 실행과 누적 지표만 보관한다. 실행 이력·DB 저장은 추가하지 않는다.

기존 `compare()` 호출 계약은 유지하거나 얇은 호환 wrapper로 제공하여 기존
adapter 테스트를 계속 활용한다. UI는 개별 완료 이벤트를 소비한다.

## 표시용 JSON 중략 정책

표시 전용 함수가 JSON 객체를 재귀적으로 복사하고 문자열 값만 중략한다.
key, object/list 구조, 숫자, boolean, null은 변경하지 않는다.

- 문자열이 480자를 초과하면 앞 320자와 뒤 120자를 남긴다.
- 가운데에 `… [중략: N자] …`를 삽입한다. N은 제외된 원문 문자 수다.
- 짧은 문자열은 그대로 표시하며 한국어와 줄바꿈을 지원한다.
- 요청 미리보기, generated output, thinking, 비 JSON 응답에도 동일 정책을 쓴다.
- 기본은 요약 보기이며 '요약 표시 · 원본 변경 없음'과 중략 건수를 표시한다.
- 전체 보기에서는 중략 없이 원문을 스크롤한다. 전체 HTTP 응답 원문도
  별도로 확인할 수 있다. 큰 내용이 다른 화면 영역을 밀어내지 않게 고정 영역을 쓴다.
- 원본 저장은 양쪽 UI에서 지원한다. 웹의 원본 복사도 요약이 아닌 전체 내용을
  사용한다. TUI에서는 클립보드 호환성에 의존하지 않고 로컬 파일 내보내기를 제공한다.
- TUI 내보내기는 프로젝트 작업 디렉토리의 `exports/`에 새 이름으로 저장하고
  기존 파일을 덮어쓰지 않는다. 이 디렉토리는 Git에서 제외한다.
  웹 저장은 브라우저의 파일 다운로드 기능을 사용한다.
- JSON 표시·저장은 UTF-8, 들여쓰기 2칸을 사용한다. 저장된 응답 원문은
  HTTPX가 디코딩한 응답 텍스트 그대로 제공한다.

## TUI 화면과 조작

Textual 전체화면 앱의 고정 header/footer와 스크롤 가능한 본문을 구성한다.

1. Header: 앱 이름, 두 실제 모델 이름, routing-only simulation 안내.
2. Scenario 영역: 6개 목록, 선택된 요청의 요약, 여러 줄 custom request 편집.
3. 비교 영역: LLM / Jev 카드. 상태를 색상과 텍스트로 표시하고 model tier,
   web, approval 결정을 가장 크게 보여준다. latency와 input/output tokens를
   강조하며 parse time·generated bytes는 세부 지표로 제공한다.
4. Inspector: router 선택과 Request JSON / Response JSON / Generated /
   Thinking 탭. 요약/전체 전환, 전체 응답 원문 보기, 내보내기를 제공한다.
5. 누적 지표: 요청·성공·오류·평균 latency 및 usage 합계.
6. Footer: Run, Next, Previous, Edit, Inspector, Quit 단축키와 실행 상태.

Enter 없이 단축키와 버튼으로 조작한다. 편집기 입력 중 일반 글자를 단축키로
가로채지 않는다. Esc로 편집을 취소할 수 있다. 긴 JSON은 syntax highlighting과
스크롤을 제공한다. 100 columns 이상은 결과를 좌우로, 좁은 터미널은 세로로
배치한다. 모든 주요 영역은 키보드 focus로 이동할 수 있다.

## 웹 화면과 통신

TUI와 같은 콘텐츠 순서에 발표용 카드, 여백, 큰 결정 배지와 숫자를 적용한다.
넓은 화면은 좌측 scenario 목록과 우측 비교/inspector를 표시하고, 좁은 화면은
세로로 배치한다. 어두운 배경과 구분되는 router 색상을 사용한다.

- 정적 페이지와 assets는 FastAPI가 제공한다.
- `/ws` WebSocket 연결 하나가 세션 하나를 소유한다.
- 연결 시 scenario와 공개 모델 이름을 전달한다.
- Run 명령은 요청 원문과 선택 scenario ID를 전달한다. 서버는 입력을 검증하고
  동시에 진행되는 두 번째 Run을 거부한다.
- 서버는 started, 개별 router result, cumulative metrics, finished 이벤트를
  run ID와 함께 보낸다. 각 이벤트의 순서를 보장한다.
- 클라이언트는 현재 run ID에 해당하는 이벤트만 적용한다. JSON 원본은 메모리에
  보관하고 화면 중략은 공통 정책의 표시 데이터로 처리한다.
- WebSocket disconnect 시 실행을 취소한다. 브라우저에는 '연결 끊김'과 재연결
  버튼을 표시한다. 재연결 시 새 세션으로 시작하며 자동 재실행하지 않는다.
- 모델 timeout/HTTP/parse 오류는 해당 카드에 표시한다. 앱 통신 오류와 모델
  오류는 구분한다. 반환된 문자열은 HTML로 삽입하지 않고 text로 렌더링한다.

## 비교 수치의 의미

기존 측정 정의를 유지한다. latency는 router별 HTTP 호출 시작부터 응답 decoding,
decision parsing/validation 완료까지이며 UI rendering·전송 시간은 제외한다.
성공 평균과 partial usage 관측 건수를 유지하고 unavailable을 0으로 바꾸지 않는다.

두 결과가 모두 성공하고 분모가 유효할 때만 latency 비율과 output-token 차이를
보여준다. 문구는 관측값 비교로 표현하며 모델 방식의 인과적 우열을 주장하지 않는다.
Ollama fallback은 generated decision임을 명시한다. expected route는 scenario
metadata로 구분하며 실제 모델 결과를 대체하지 않는다.

## 검증과 완료 기준

- 기존 47개 테스트를 회귀 검증한다.
- HTTP 요청 바디가 실제 전송 payload와 동일하고 성공·오류 모두에서 기록되는지,
  parser 결과 교체 후에도 HTTP 기록이 보존되는지 MockTransport로 검증한다.
- 중략이 원본 객체를 변경하지 않으며 경계 길이, 중첩 구조, 한국어, 저장 원본을
  올바르게 처리하는지 검증한다.
- 완료 순서가 다른 두 router에서 빠른 결과가 먼저 전달되고 한쪽 오류가 다른
  결과를 막지 않는지, 지표가 중복 집계되지 않는지 검증한다.
- Textual Pilot으로 실행, scenario 전환, 편집, inspector, 단축키 focus,
  좁은 화면과 긴 JSON 스크롤의 주요 동작을 검증한다.
- 웹은 테스트 client로 세션·이벤트·오류 계약을 검증하고 브라우저에서 mock
  backend를 이용해 실행·부분 완료·실패·요약/전체·복사/저장을 확인한다.
- 정적 assets가 배포 패키지에 포함되고 TUI/웹 명령으로 실행되는지 확인한다.
- 실제 모델 endpoint를 사용한 검증은 실행 가능한 설정이 있을 때 수행하고,
  mock 검증과 실제 호출 결과를 완료 보고에 구분한다.
- README에 두 실행 방법, JSON 중략/원본 저장, 단축키, 측정 해석을 반영한다.
- 구현과 검증 후 작업 브랜치를 커밋·푸시하고 PR을 생성한다. 병합은 별도 승인을 받는다.
